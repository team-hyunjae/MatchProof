# 결혼정보업체의 서류 없는 조건 확인 — MatchProof(가칭)

작성일: 2026-09-21. 사용자가 선택한 첫 시연 대상은 결혼정보업체의 소득·혼인 관련 가입 심사다. 아래 세부 기준은 해커톤 구현을 위한 제안이며 실제 업체의 심사 정책이나 공식 서류 연동이 아니다.

## 제품 방향

검증기관이 확인한 자격증명을 이용해, 결혼정보업체가 소득·혼인 관련 서류 원본을 수집·보관하지 않고 정해진 가입 조건의 충족 여부를 확인하는 모듈을 만든다. 고객은 결혼정보업체, 이용자는 가입 신청자다. 기존 가입 화면에 붙일 수 있는 심사 흐름을 시연한다.

핵심 가설은 '가입 심사에 필요한 사실의 신뢰성은 유지하면서 원본 서류의 재제출과 업체별 사본 보관을 줄일 수 있다'이다. 실제 업체의 도입 의사, 원본이 필요한 업무 범위와 비용 절감 규모는 아직 확인하지 않았다.

## 첫 데모

가상 심사 정책 하나를 사용한다. 예: **2025년 확인된 연간 소득 5,000만 원 이상 + 확인 기준일에 혼인 중이 아님**. 금액·연도는 임의의 테스트 값이며 바람직한 결혼 조건이나 실제 업체 기준을 의미하지 않는다. 과거 연간 소득을 현재 연봉이나 재직 여부로 표현하지 않는다.

1. 모의 검증기관이 가상 자료를 확인하고 신청자의 소득·기준연도·혼인 상태·확인시각·만료시각이 포함된 자격증명을 발급한다.
2. 결혼정보업체가 인증된 가입 세션에 대해 1회용 심사 요청을 만든다. 요청은 신청자의 키, 업체의 배포, 요청별 비밀 난수에 결합한다.
3. 신청자는 수신 업체, 요구 조건, 공개되는 결과, 유효기간을 확인하고 증명을 제출한다.
4. 계약이 발급 사실, 신청자의 키 소유, 조건, 자료의 신선도와 요청 유효기간을 함께 확인한다.
5. 업체는 자신이 만든 요청의 확정 결과를 조회한다. 업체 화면에는 **조건 충족 / 확인 미완료 / 확인 기한 만료**와 해당 요청의 유효기간을 표시한다.

실패 사유는 신청자의 로컬 화면에서만 안내한다. 증명 미제출과 특정 조건 미충족을 업체가 구별할 수 있다고 주장하지 않는다. 확정 전에는 '확인 중'이다. 과거 승인 기록이 남아 있어도 만료된 기록을 현재 유효한 인증 배지로 표시하지 않는다.

## 무엇을 누구에게 숨기는가

| 정보 | 모의 검증기관 | 신청자 기기 | 결혼정보업체 | 공개 체인 |
| --- | --- | --- | --- | --- |
| 가상 원본 자료·정확한 소득·혼인 상태 | 확인 | 본인 자료 보유 | 전달하지 않음 | 기록하지 않음 |
| 신청자 비밀키 | 전달하지 않음 | 생성·보관 | 전달하지 않음 | 기록하지 않음 |
| 자격증명·발급용 난수 | 생성/확인 | 암호화 보관 예정 | 전달하지 않음 | 난수로 숨긴 commitment만 공개 |
| 가입 계정과 심사 요청의 대응관계 | 전달하지 않음 | 본인 세션 | 세션 시스템에 보관 예정 | 계정·실명 기록 없음 |
| 고정 심사 조건, 요청 시각·만료, 요청 식별값, 승인 기록 | 공개 정보 조회 가능 | 공개 정보 조회 가능 | 조회 | 공개 |

**원본을 보는 주체가 사라지는 것은 아니다.** 검증기관의 확인을 신뢰하고, 결혼정보업체에 원본을 다시 넘기지 않는 구조다. 업체 자신이 서류를 받아 발급까지 한다면 '업체가 원본을 보지 않는다'는 설명은 성립하지 않는다. 검증기관의 자료 보관·접근 통제는 별도 문제다.

결과도 정보다. 업체는 승인 결과로 두 조건을 충족한다는 사실을 알게 된다. 공개 정책과 성공 거래를 계정에 연결할 수 있는 관찰자도 같은 사실을 추론할 수 있다. 요청 시각, 지갑·네트워크 정보, 작은 사용자 집합에 따른 연결 위험이 있으므로 '완전 익명'이나 '아무 정보도 공개하지 않음'을 주장하지 않는다.

`혼인 중이 아님`은 `혼인 경험이 없음`과 다르다. 이 데모는 과거 혼인 이력을 공개하거나 구분하지 않는다. 확인 이후 상태 변경을 실시간으로 감지하지 않으므로 '지금 확실히 미혼인 사람'을 보증하는 배지로 쓰지 않는다.

## Midnight을 쓰는 이유와 한계

ZK 회로는 비공개 자료가 기관이 등록한 자격증명과 같은지, 그 자료가 공개된 조건을 충족하는지 확인한다. 공개 계약은 발급 권한·심사 요청·요청 소비 상태를 검증 가능하게 관리한다. 업체는 원본 자료나 신청자 API를 신뢰하는 대신 자신의 요청과 연결된 확정 결과를 읽는다.

단순한 서류 보관 축소는 중앙화 검증 서비스로도 가능하다. 이 MVP에서 Midnight의 역할은 비공개 조건 검증과 공동으로 확인 가능한 요청 상태이며, 블록체인만이 유일한 해법이라고 주장하지 않는다. 웹사이트 로그인 인증, 실제 사람과 키의 연결, 허위 서류 식별, 검증기관의 부정 발급은 ZK만으로 해결되지 않는다.

## 계약 초안과 구현 상태

`contracts/matchproof.compact`는 기존 식권 계약과 분리되어 있다.

- `issue`: 발급기관 비밀키 소유를 확인하고 자격증명 commitment를 등록한다. 자격증명에는 holder commitment와 32바이트 무작위 salt를 포함한다. 발급기관은 신청자 비밀키를 받지 않는다.
- `openRequest`: 업체 권한으로 요청을 등록한다. 생성 시각은 블록 시각과 가까워야 하며 최대 10분 동안만 유효하다.
- `proveEligibility`: 신청자 키, 등록된 자격증명의 Merkle 경로, 소득·기준연도·혼인 조건, 비공개 확인시각·만료시각, 요청별 binding을 확인한다. 성공한 요청은 한 번만 소비한다.
- 심사 조건은 배포 때 고정한다. 데모는 소득 기준을 반복해서 바꾸어 정확한 소득을 좁혀가는 기능을 제공하지 않는다. 별도 배포에서의 반복 질의까지 자동으로 막는 것은 아니다. 후속 동의 화면이 실제 조건과 수신자를 표시해야 한다.
- 신청자의 확인시각과 자료 만료시각은 비공개다. 블록 시각 검사의 경계값은 공개되므로, 회로 안에서 비공개 시각을 공개 요청 구간과 비교하도록 구현했다.
- 동일 배포에서는 새 요청을 만들어 재심사할 수 있다. 식권의 하루 1회 제한은 사용하지 않는다. 타 업체 배포로 요청을 복사해도 동일 증명을 승인하지 않도록 배포별 난수를 결합한다.
- 기관의 확인 자료는 데모 기준 최대 7일 전까지 허용하며, 자료 유효기간과 신선도는 심사 요청의 전체 유효기간을 포함해야 한다. 이는 실제 업무에 적합하다고 검증된 기간이 아니다.

현재 **전체 Compact 컴파일·증명 키 생성과 자동 검사 36개**를 통과했다. MatchProof 계약 검사 13개, 파일 전달·보관·기간·재발급 검사 6개, 기존 회귀 검사 17개다. 핵심 검사는 발급·업체 권한, 소득 변조, 가짜 발급 경로, 키 소유, 소득·연도·혼인 조건, 미래·만료·오래된 자료, 요청/배포 결합, 중복 요청 및 만료 경계다.

`/matchproof`에 기관·신청자·업체 화면을 추가했다. 로컬 개발 네트워크에서 새 계약 배포 → 발급 → 심사 요청 → ZK 증명 확정 → 별도 공개 조회를 완료했다. 신규 경로는 `undeployed`만 허용한다. CLI 검사는 역할별 메모리 상태와 개발용 수수료 지갑 하나를 사용하며, 브라우저는 역할·지갑·배포별 암호화 IndexedDB 보관함을 사용한다. 기존 `/`와 `/network`는 QuietPass로 남겨 두었다.

현재 업체의 가상 접수번호와 요청 연결은 해당 업체 기기의 암호화 상태에 저장한다. **실제 회원 로그인·직원 권한·서버 세션 연동은 아직 없다.** 기존 QuietPass의 거래를 새 계약의 증거로 대체하지 않는다. 실행 방법과 검증 경계는 [MatchProof runbook](matchproof-runbook.md)을 따른다.

```sh
npm run matchproof:check
npm run typecheck
npm test
```

## 남은 개발 순서

| 단계 | 완료 기준 |
| --- | --- |
| 1. 핵심 계약 | 완료: 조건·기관 신뢰·요청 결합·만료를 컴파일된 계약에서 검사 |
| 2. 역할별 화면 | 완료: 모의 검증기관 / 신청자 동의·증명 / 업체 심사함, 가상 자료만 사용 |
| 3. 개발 네트워크 연결 | 완료: 로컬 `undeployed`에서 새 계약으로 발급 → 요청 → ZK 증명 → 별도 업체 조회 |
| 4. 계정·개인 상태 경계 | 암호화 보관·가상 접수 연결·새로고침 복구 구현. 실제 로그인·지갑 확장 승인·독립 기기 재현은 후속 검증 |
| 5. 비교·발표 | 최종 후보 선택 완료. 새 환경 재현·제출 자료·발표 리허설 |

MatchProof의 재현성과 제출 자료를 마무리하고 발표를 리허설한다.

## 첫 제출 범위에서 제외

공공기관·금융기관 서류 API 연동, 실제 소득·가족관계 서류 수집, OCR 진위 판정, 다중 발급기관, 즉시 개별 철회, 비밀키 복구, 동일인 중복 계정 차단, 상대방 프로필 공개, 추천·매칭·채팅·결제는 후속 범위다. 사용자가 제어하는 로컬 증명 서버와 암호화 저장소는 기존 구현을 재사용할 후보이며 새 흐름에서 다시 검증해야 한다.

## 레퍼런스 점검

- [Midnight 공식 문서](https://docs.midnight.network/): 비공개 입력과 선택적 공개의 기반. 이 문서는 기능 설명이며 현실의 서류 진위를 보장하는 서비스가 아니다.
- [공식 awesome dApps 목록](https://github.com/midnightntwrk/midnight-awesome-dapps): 레퍼런스 탐색용. 목록 자체도 커뮤니티 코드의 동작을 보장하지 않는다고 안내한다.
- [Brick Towers Midnight Identity](https://github.com/bricktowers/midnight-identity): README의 검증기관 발급 → 사용자 보관 → 필요한 속성 검증 흐름을 참고했다. 기존 지갑·서명 레지스트리 구조를 그대로 도입하지 않았다.
- [Credence](https://github.com/0xfdbu/midnight-apps/tree/main/fullstack-dapp): 기관이 등록한 credential과 Merkle membership 방식의 비교 자료. README를 확인했으며 이 세션에서 해당 앱의 실행이나 전체 코드 감사를 수행하지 않았다.
- [Proof-of-Age Gate](https://github.com/tomiin/midnight-proof-of-age): README가 사용자 입력 출생연도에서 시작한다. 조건 검증 예제로 참고할 수 있으나 해당 설명만으로 공인 신원·서류 인증이 갖춰졌다고 판단하지 않았다.

차별화 목표는 범용 나이 인증이 아니라, **결혼정보 가입 심사에서 원본 서류 대신 무엇을 요청·공개·보관할지 명확히 보여주는 업무 흐름**이다. 레퍼런스에 같은 아이디어가 전혀 없거나 최초라는 주장은 하지 않는다.
