# MatchProof 심사위원 데모 가이드

[English](matchproof-judge-guide.en.md) · [한국어](matchproof-judge-guide.md)

결혼정보업체는 소득·혼인 관련 서류의 사본을 보관하지 않고, 신청자가 동의한 가입 조건의 충족 여부를 확인합니다.

**시연 범위:** 가상 자료와 Midnight 로컬 개발 네트워크(`undeployed`). 실제 공공기관 서류·실제 회원 계정과 연동하지 않습니다.

## 1. 누가 무엇을 하나요?

| 역할 | 하는 일 | 볼 수 있는 정보 |
| --- | --- | --- |
| 모의 검증기관 | 가상 자료를 확인하고 신청자에게 자격증명을 발급 | 정확한 가상 소득과 확인 기준일의 혼인 상태 |
| 신청자 | 자격증명을 보관하고, 업체의 요청과 공개 범위를 확인한 뒤 조건 증명 | 본인의 가상 자료, 수신 업체, 조건, 요청 기한 |
| 결혼정보업체 | 심사 요청을 만들고 체인에서 확정된 결과 조회 | 공개 조건·요청·기한·조건 충족 기록. 정확한 소득액과 원본은 받지 않음 |
| 심사위원 | 지갑이나 자격증명 파일 없이 별도 화면에서 같은 체인 기록 조회 | 업체의 공개 조회 화면과 같은 정보 |

## 2. 지금 바로 확인하기 — 지갑 없이 기존 기록 조회

[README 설치 절차](../README.ko.md)를 완료하고 개발 서비스와 앱을 실행해야 합니다. 새 clone에는 이전 시연 주소가 포함되지 않습니다. 새 배포를 준비하거나 `npm run matchproof:smoke`로 조회 대상을 만든 뒤 진행합니다.

1. [MatchProof 열기](http://127.0.0.1:4180/matchproof).
2. **결혼정보업체 → 개발 네트워크 연결 설정 → 최근 시연 불러오기**를 누릅니다. 설정이 접혀 있으면 먼저 펼칩니다.
3. 등록된 심사 요청, 확정된 심사 기록, 각 요청의 상태를 확인합니다.
4. **별도 업체 화면 열기 ↗**를 누릅니다. 새 화면의 **체인 기록 조회**를 누릅니다. 새 창은 자동 조회하지 않습니다.
5. 두 화면의 배포 주소·공개 요청 식별값·승인 기록이 같은지 확인합니다. 지갑·보관 암호·신청자 파일을 입력하지 않아도 조회됩니다.

최근 시연 주소는 마지막 CLI 검사 실행에 따라 달라집니다. 승인 기록이 있어도 요청 후 10분이 지나면 **기한 만료**가 정상입니다. 이는 과거 승인 기록이며 현재 유효한 인증은 아닙니다. 새로 ‘조건 충족’을 보여주려면 아래 절차로 새 요청을 만들어야 합니다.

이 주소의 `127.0.0.1`은 주소를 여는 사람의 컴퓨터입니다. 현재는 발표자 기기에서 직접 체험하는 방식입니다. 주소만 심사위원의 다른 노트북으로 전달해서 같은 네트워크에 접속할 수 있는 상태는 아닙니다.

## 3. 새 심사를 시연하기 전 준비 — 발표자용

- 개발 노드(9944), 인덱서(8088), 증명 서버(6300)를 준비합니다. 프로젝트에서 `npm run doctor:network` → `npm run demo`를 실행하고 `DEMO READY` 이후 4180 화면을 엽니다. 이 명령은 수동 시연용 테스트 지갑 연결도 함께 제공합니다. 일반 `preview`에는 테스트 지갑이 자동 연결되지 않습니다.
- 신규 배포·발급·요청·증명에는 개발용 잔액과 Connector 4.x 지갑 연결이 필요합니다. 네트워크는 `undeployed`, 인덱서는 loopback 8088, 증명 서버는 loopback 6300 주소입니다. 이 포트가 SSH 터널이면 실제 처리는 연결된 서버에서 이루어집니다.
- 일반 preview에는 지갑이 자동 연결되지 않습니다. `npm run demo`로 시작한 화면에서는 개발용 테스트 지갑을 사용하며, 거래는 자동 서명됩니다. 실제 확장 승인창이 없다는 점을 설명합니다. 공개 조회에는 지갑이 필요 없습니다.
- 역할마다 창/탭을 나누고 보관함을 연결합니다. 별도 프로필을 쓰면 각 프로필의 지갑도 먼저 준비합니다. 역할을 바꾸거나 새로고침한 뒤에는 같은 지갑·역할·보관 암호로 다시 연결합니다. 암호는 16자 이상, 대문자·소문자·숫자·기호 중 3종류 이상입니다.
- 별도 공개 조회용 창은 지갑과 보관함을 연결하지 않습니다. 같은 프로필의 새 탭은 저장소를 공유하므로, 저장소까지 분리된 검증을 보여주려면 별도 프로필/브라우저를 씁니다.
- `최근 시연 불러오기`는 저장된 시연 주소를 읽습니다. **브라우저에서 새로 배포한 계약은 자동으로 이 버튼의 조회 대상이 되지 않습니다.** 새 배포 주소를 복사해서 조회하거나 새 배포의 ‘별도 업체 화면 열기’ 링크를 사용합니다.

아래 1~5단계는 발표 전에 준비할 수 있습니다. **10분 제한이 있는 심사 요청은 발표 직전에, 신청자가 바로 증명할 수 있을 때 생성합니다.**

## 4. 역할별 클릭 순서와 확인 기준

| 순서 | 조작하는 역할 | 화면에서 할 일 | 심사위원이 확인할 결과 |
| --- | --- | --- | --- |
| 1 | 업체 | 보관 암호 입력 → **개발용 지갑 연결**. ‘검증기관에 전달할 업체 등록값’을 복사 | 기관이 앞으로 사용할 업체 등록값 준비. 아직 배포 주소는 없어도 됨 |
| 2 | 모의 검증기관 | 보관 암호 입력 → **개발용 지갑 연결**. ‘업체가 전달한 등록값’ 입력 → **개발 네트워크에 배포** | 확정 후 프로그램 배포 주소와 ‘체인에서 확정된 거래’가 표시됨 |
| 3 | 업체·신청자 | 같은 프로그램 배포 주소 입력. 각각 지갑 연결 후 **이 배포에 연결**. 신청자는 ‘신청자 등록값’을 기관·업체에 전달 | 모두 같은 배포에 연결. 신청자 등록값과 비밀키는 다른 값이며 비밀키를 전달하지 않음 |
| 4 | 모의 검증기관 | 신청자 등록값 입력. ‘가상 확인 자료’에서 **2025년 6,500만 원 · 확인일에 혼인 중 아님** 선택 → **가상 자격 발급** → 확정 후 **파일 받기** | `matchproof-credential.json`을 해당 신청자에게만 전달. 발급 거래 확정 확인 |
| 5 | 신청자 | **자격증명 가져오기**에서 기관의 파일 선택 | ‘나만 보는 가상 자료’에 2025년 소득 65,000,000원과 기준일 상태 표시. 파일과 체인 발급 기록의 일치 검사 |
| 6 | 업체 | ‘가상 접수번호’에 `DEMO-001`, ‘신청자 등록값’ 입력 → **심사 요청 만들기** → 확정 후 **파일 받기** | 요청 행이 ‘확인 미완료’. `matchproof-request.json`을 해당 신청자에게 전달 |
| 7 | 신청자 | **심사 요청 가져오기**에서 업체의 파일 선택 | 수신 업체·2025년 소득 5,000만 원 이상·기준일에 혼인 중 아님·최신성 7일·요청 기한을 확인할 수 있음 |
| 8 | 신청자 | 동의하지 않은 상태의 비활성화 버튼 확인 → 동의 체크 → **동의하고 조건 증명하기** → 확장 사용 시 지갑 승인; 테스트 지갑은 개발 거래 자동 서명 | 증명 생성·거래 제출 중에는 완료로 표시하지 않음. ‘심사 증명이 확정됐어요’와 확정 거래가 나온 뒤 다음 단계로 이동 |
| 9 | 업체 | **최신 상태 확인** | 같은 요청이 기한 내 ‘조건 충족’으로 표시됨. 정확한 소득 6,500만 원과 원본은 이 화면에 없음 |
| 10 | 심사위원 | **별도 업체 화면 열기 ↗**의 주소를 독립 조회 창에서 열고 **체인 기록 조회** | 신청자 파일·비밀키·지갑 연결 없이 동일한 공개 요청의 승인 기록 확인 |

예상 발표 순서는 ‘기관이 확인하고 → 신청자가 동의하고 → 업체가 결과만 읽는다’입니다. 최초 설정만 업체 등록값이 필요하므로 업체가 먼저 시작합니다.

가상 자격증명 JSON에는 정확한 소득·기준일 상태·발급용 난수가, 요청 JSON에는 비공개 nonce가 포함됩니다. 자격 파일을 업체 화면으로 전달하는 시연을 하지 않습니다. 파일 전달은 이 MVP의 수동 절차이며 실제 서류 업로드 기능이 아닙니다.

## 5. 실패 조건도 직접 확인하기

성공 시연을 먼저 끝내고 별도 접수번호 `DEMO-FAIL-001`로 진행합니다. 각 검사는 새 미사용 요청을 만들고 기한 안에 수행합니다.

| 검증 | 조작 | 기대 결과 |
| --- | --- | --- |
| 소득 조건 미충족 | 기관에서 동일 신청자에게 ‘2025년 3,000만 원 · 소득 조건 미충족’으로 새 자격 발급 → 신청자가 이 파일로 교체 → 새 요청을 가져와 증명 시도 | 신청자에게 소득 미달 안내. 업체의 새 요청은 ‘확인 미완료’이며 승인 건수가 늘지 않음. 업체 화면에 소득액·실패 사유가 표시되지 않음 |
| 혼인 조건 미충족 | 기관에서 ‘확인일에 혼인 중’ 자료 발급 → 신청자가 가져와 새 요청으로 증명 시도 | 신청자에게 혼인 조건 미충족 안내. 업체에는 성공 기록이 생기지 않음 |
| 동의하지 않음 | 자격·요청을 가져온 뒤 동의 체크를 하지 않음 | ‘동의하고 조건 증명하기’ 버튼 비활성화. UI의 동의 확인을 보여주는 검사 |
| 이미 승인된 요청 | 성공한 요청을 신청자 화면에서 다시 확인 | 다시 증명하는 버튼 비활성화. SDK 수준의 재사용 거절은 아래 자동 검증 기록으로 보완 |
| 요청 만료 | 만료된 요청 조회 | ‘기한 만료’. 과거 승인 기록이 있어도 현재 유효한 인증으로 표시하지 않음 |

‘확인 미완료’만으로 소득 미달인지, 미동의인지, 아직 처리 중인지 구별할 수 없습니다. 실패 이유를 공개하지 않는 설계입니다. 기한이 지나면 ‘기한 만료’로 바뀝니다.

소득·혼인 조건 실패는 제출 전 SDK 회로 실행에서 거절됩니다. 이를 실패 거래가 체인에 채굴된 것으로 설명하지 않습니다. UI 버튼 비활성화만으로 계약의 재사용 방지가 검증됐다고 설명하지도 않습니다. 계약·클라이언트 검사와 실제 체인 성공 거래의 증거는 [검증 안내](validation.md)를 함께 제시합니다.

## 6. 발표할 때 사용할 설명

> “기관은 가상 자료의 내용을 알고 자격을 발급합니다. 신청자는 어떤 업체가 어떤 조건을 확인하는지 보고 동의합니다. Midnight 개발 네트워크에서 증명이 확정되면, 업체는 원본이나 정확한 소득액을 받지 않고 조건 충족 기록을 확인합니다. 이제 심사위원이 신청자의 보관함 없이 같은 기록을 조회해 보겠습니다.”

5분 발표를 목표로 한다면 설정·배포·자격 발급은 미리 끝내고, 문제 설명 40초 → 새 요청 생성 40초 → 신청자 동의·증명 90초 → 독립 조회 60초 → 실패 사례·한계 70초로 배분합니다. 이는 발표 시간 배분안이며, 체인 확정 속도를 보장하는 수치는 아닙니다. 리허설에서 여유 시간을 조정합니다.

시연 후 판단할 핵심은 다음과 같습니다.

- 발급받은 자료와 신청자 키에 맞는 증명만 성공하는가?
- 신청자가 수신자·조건·기한·공개 결과를 확인할 수 있는가?
- 업체가 정확한 소득액과 원본 없이 승인 기록을 조회하는가?
- 새 공개 조회 창에서도 같은 체인 결과가 나오는가?
- 실패·미동의·만료를 성공으로 표시하지 않는가?

화면의 ‘업체로 전달하는 원본 0건’은 데모 설계를 설명하는 고정 표시이며 트래픽 감사 계측값은 아닙니다. 이 문구만을 개인정보 비노출의 증거로 삼지 않고, 역할별 화면·파일 전달 경로·공개 원장 구조를 함께 설명합니다.

## 7. 질문에 답할 때 구분할 범위

- **기관 신뢰:** 실제 서류의 진위를 Midnight이 자동 확인하는 구조가 아닙니다. 이 데모는 모의 발급기관이 확인한 자료에 의존합니다.
- **보호 범위:** 업체의 서류 사본 보관을 줄입니다. 발급기관은 원본 내용을 알고, 증명 서버는 비공개 입력을 처리합니다. 이 기기의 개발 포트는 SSH 전달일 수 있으므로 실제 서버 위치를 확인하지 않고 동일 기기 내 처리라고 주장하지 않습니다.
- **공개 범위:** 정책·요청·기한·성공 기록은 공개됩니다. 요청이 사람과 연결되면 조건 충족 사실을 추론할 수 있으므로 완전 익명을 주장하지 않습니다.
- **상태의 의미:** 확인 기준일의 혼인 상태를 증명합니다. 현재 혼인 상태나 과거 혼인 이력 전체를 보증하지 않습니다.
- **만료와 파기:** 10분 만료 후 신규 증명을 허용하지 않고 현재 유효한 인증으로 표시하지 않습니다. 공개 요청·승인 기록은 체인에 남으며 현재 계약에는 삭제·즉시 철회 기능이 없습니다. 만료만으로 개인정보 파기 의무를 충족했다고 설명하지 않습니다.
- **현재 구현:** `DEMO-001`은 기기에 보관하는 가상 접수번호입니다. 실제 회원 로그인·직원 권한 시스템은 아직 없습니다.
- **지갑 검증:** 기존 전체 브라우저 검증은 공식 테스트 지갑 어댑터를 사용했습니다. 실제 확장 지갑의 승인창 검증과 독립 물리 기기 재현은 별도입니다. 어댑터를 사용하는 발표에서는 ‘개발용 테스트 지갑으로 서명’한다고 명시합니다.

## 8. 막혔을 때 복구

| 증상 | 대응 |
| --- | --- |
| 4180 페이지가 안 열림 | 프로젝트 폴더에서 `npm run demo`를 실행하고 `DEMO READY` 확인. 실행 터미널 유지. 조회만 필요하면 `npm run preview`도 가능 |
| 페이지는 열리지만 조회 실패 | 인덱서 8088과 배포 주소 확인. 개발 체인을 초기화했다면 기존 주소 대신 새 배포 필요 |
| 개발용 지갑 연결 버튼 비활성화 | 보관 암호 길이 확인. 실제 연결 시 암호 복잡성도 검사됨 |
| 지갑 확장이 필요하다는 안내 | 수동 시연은 `npm run demo`로 실행하고 페이지 새로고침. 화면의 테스트 지갑 준비 안내 확인. 공개 조회만 하려면 지갑 연결 없이 ‘체인 기록 조회’ 사용 |
| 동의했는데 조건 증명 버튼 비활성화 | 신청자 화면에 ‘나만 보는 가상 자료’가 있는지 확인. 없으면 기관의 `matchproof-credential.json`을 ‘자격증명 가져오기’에서 선택. 업체의 요청 파일만으로는 증명할 수 없음. 요청 만료·이미 승인된 상태도 확인 |
| 새 심사 요청·자격 발급 버튼 비활성화 | 역할별 지갑 연결 후 같은 주소로 ‘이 배포에 연결’, 신청자 등록값 입력 여부 확인 |
| 업체/기관 키가 다르다는 안내 | 최초 등록·배포한 역할의 지갑·브라우저 보관함으로 복귀. 공개 조회 권한과 신규 거래 권한은 다름 |
| 새 창이 비어 보임 | 주소만 전달된 상태이므로 ‘체인 기록 조회’ 클릭 |
